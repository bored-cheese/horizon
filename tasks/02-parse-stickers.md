# Задача 2. Разбор новых стикеров и связей

> Требует инструкций проекта «Горизонт»: разделы «Что такое потребность»,
> «Геометрия фрейма» и «Как писать». Вне проекта задача работать не будет.

**Пишет на доску:** да — правит текст стикеров и цвет связей.
**Пишет в таблицу:** да — добавляет строки.
**Периодичность:** вручную, после добавления стикеров.

## Что прочитать

Из таблицы «Реестр потребностей» — все строки, колонки `id`, `type`,
`needs`, `p_id`, `depends on`, `Примечания`. И максимальный `id`.

С доски — стикеры внутри фрейма «Горизонт планирования» и линии между ними.
У линии нужны оба конца и текущий цвет.

Стикеры за пределами фрейма не трогай. Стикеры без текста пропускай.

## Часть 1. Новые стикеры

Найди стикеры без ID в тексте — это новые потребности, добавленные вручную.

Каждый сначала проверь на признак решения и на признак хотелки.
Не прошло проверку — строку не заводи, вынеси на уточнение с предложением, как переформулировать.

Для прошедших проверку:

1. Определи год по центру стикера, из года — период.

2. Определи важность и `type` по дорожке, в которой лежит стикер.

3. Заведи строку: присвой `id` на единицу больше максимального в таблице, проставь `type`, `period`, `importance`, текст стикера положи в `needs`.

4. Заполни `p_id` — id корневой потребности, ради которой существует эта. Бери только из прочитанных строк с `type` = root. Если подходят две — оставь пусто и вынеси на уточнение с обеими. Если корневых в таблице ещё нет — оставь пусто, это не ошибка.

5. Остальные колонки оставь пустыми — их заполнит задача 3 по комментариям.

6. Перепиши текст стикера, добавив в начало присвоенный id и разделитель « · ». Если текст стикера обёрнут в ссылку, сохрани обёртку: id должен войти внутрь ссылки, а не заменить её.

## Часть 2. Связи

Для каждой линии определи id обоих стикеров — он написан в начале текста
стикера, до разделителя « · ». Затем посмотри `type` этих потребностей
в таблице. Дальше действуй по одному из трёх случаев.

### Случай А. Хотя бы у одной из двух `type` = root

Это принадлежность, а не зависимость.

**Направление не определяй.** Вертикальное положение здесь не значит
ничего: корневая потребность не веха, раньше или позже она не наступает.
Не сравнивай центры, не пиши «направление не определено».

- В строку НЕ-корневой потребности, в колонку `p_id`, запиши `id` корневой.
  Одно число, не список.
- Строку корневой потребности не трогай: у корневых `depends on` пустой.
- Цвет линии поменяй на `#e7e7e7`, если он другой.

### Случай Б. У обеих `type` = derivative

Это зависимость по времени. Только здесь определяется направление.

Кто ниже на доске, тот наступает раньше и является предшественником:
запиши `id` нижнего в `depends on` верхнего.

Сравнивай центры по вертикали, а не годовые полосы. Два стикера в одной
полосе почти всегда стоят на разной высоте, и этого достаточно.

Если центры совпадают с точностью до нескольких пикселей, направление
не определяется. Связь всё равно зафиксируй: запиши в `Примечания` обоих
«связь с N, направление не определено» и вынеси пару на уточнение.

### Случай В. У обеих `type` = root

Связь между двумя корневыми потребностями схемой не предусмотрена.
Ничего не записывай, вынеси пару на уточнение.

### Перед любой записью

Посмотри, что уже лежит в ячейке. Если id там уже есть — не добавляй
повторно. Если в ячейке есть id, которому не соответствует ни одна линия
на доске, — не удаляй его, а вынеси в список расхождений: возможно,
связь проставлена вручную.

Если у корневой потребности в `depends on` что-то стоит — это след
прошлых прогонов. Не исправляй молча, вынеси в расхождения.

## Что вернуть

1. Заведённые строки.
2. Отложенные на уточнение: решения вместо потребностей и хотелки.
3. Связи без определимого направления.
4. Расхождения по связям: id, который стоит в `depends on` или `p_id`,
   но которому не соответствует ни одна линия на доске.
